# Feature Specification: เมนูนำทางระบบและหน้าจอการจัดการสิทธิ์

**Feature Branch**: `003-menu-permission-management`

**Created**: 2026-09-11

**Status**: Draft

**Input**: User description: "เพื่มเมนูของระบบ และเพิ่มหน้าจอการจัดการสิทธิ์"

## Clarifications

### Session 2026-09-11

- Q: เมื่อพนักงานลืมรหัสผ่าน ผู้ดูแลระบบ (Admin) ควรมีวิธี "รีเซ็ตรหัสผ่าน" ให้พนักงานคนนั้นผ่านหน้าจอจัดการสิทธิ์นี้หรือไม่? → A: Admin ตั้งรหัสผ่านใหม่ให้พนักงานโดยตรงผ่านหน้าจอนี้ (คล้ายตอนสร้างบัญชีใหม่) พนักงานใช้รหัสผ่านนั้นล็อกอินได้ทันที
- Q: ประวัติการเปลี่ยนแปลงบัญชีพนักงาน (Staff Audit Log) จำเป็นต้องมีหน้าจอให้ Admin ดูย้อนหลังได้ในเวอร์ชันนี้หรือไม่? → A: บันทึกเก็บไว้ในระบบ (ฐานข้อมูล) เท่านั้น ยังไม่ต้องมี UI แสดงผลในเวอร์ชันนี้

## User Scenarios & Testing *(mandatory)*

### User Story 1 - เข้าถึงทุกหน้าจอผ่านเมนูนำทางเดียว (Priority: P1)

พนักงานหรือผู้ดูแลร้านล็อกอินเข้าระบบแล้วเห็นเมนูนำทางกลางที่แสดงรายการหน้าจอทั้งหมดที่ตนมีสิทธิ์ใช้งาน (เช่น ขายสินค้า, สต็อกสินค้า, โปรโมชั่น, ประวัติการขาย, รายงาน, จัดการสิทธิ์) สามารถคลิกเพื่อสลับไปยังหน้าจอต่าง ๆ ได้โดยไม่ต้องพิมพ์ URL เอง และเห็นว่าตนเองกำลังอยู่หน้าใด

**Why this priority**: ปัจจุบันระบบยังไม่มีเมนูนำทางกลาง ผู้ใช้ต้องรู้ URL ของแต่ละหน้าเอง การมีเมนูกลางเป็นพื้นฐานให้ผู้ใช้ทุกคนใช้งานระบบได้จริงในชีวิตประจำวัน และเป็นจุดที่ใช้เข้าถึงหน้าจอจัดการสิทธิ์ใหม่ (User Story 2) ด้วย

**Independent Test**: ล็อกอินด้วยบัญชี Cashier และบัญชี Admin แยกกัน ตรวจสอบว่าเมนูที่แสดงตรงกับสิทธิ์ของแต่ละ Role และคลิกแต่ละรายการเมนูแล้วระบบพาไปหน้าจอที่ถูกต้อง

**Acceptance Scenarios**:

1. **Given** พนักงาน Role "Cashier" ล็อกอินสำเร็จ, **When** ระบบแสดงหน้าจอใด ๆ ภายในระบบ, **Then** เมนูนำทางแสดงเฉพาะรายการที่ Cashier มีสิทธิ์เข้าถึงตามกฎสิทธิ์เดิมของระบบ คือ "ขายสินค้า" เท่านั้น และไม่แสดงรายการที่สงวนไว้สำหรับ Admin (สต็อกสินค้า, โปรโมชั่น, ประวัติการขาย, รายงาน, จัดการสิทธิ์)
2. **Given** ผู้ดูแลร้าน Role "Admin" ล็อกอินสำเร็จ, **When** ระบบแสดงหน้าจอใด ๆ ภายในระบบ, **Then** เมนูนำทางแสดงรายการหน้าจอทั้งหมดที่มีในระบบ รวมถึงหน้าจอ "จัดการสิทธิ์"
3. **Given** ผู้ใช้กำลังอยู่ในหน้าจอใดหน้าจอหนึ่ง, **When** ดูเมนูนำทาง, **Then** รายการเมนูของหน้าจอปัจจุบันถูกไฮไลต์หรือแสดงสถานะ active ให้เห็นชัดเจน
4. **Given** ผู้ใช้คลิกรายการเมนูที่ไม่ใช่หน้าปัจจุบัน, **When** ระบบประมวลผล, **Then** ระบบพาไปยังหน้าจอที่เลือกโดยไม่ต้องโหลดหน้าใหม่ทั้งหมด (client-side navigation)
5. **Given** ผู้ใช้ยังไม่ได้ล็อกอิน, **When** พยายามเข้าถึงหน้าใด ๆ ของระบบ, **Then** ระบบไม่แสดงเมนูนำทางและนำผู้ใช้ไปหน้าล็อกอิน (พฤติกรรมเดิมของระบบ)

### User Story 2 - ผู้ดูแลระบบจัดการบัญชีพนักงานและสิทธิ์ (Priority: P2)

ผู้ดูแลระบบ (Admin) เข้าหน้าจอ "จัดการสิทธิ์" เพื่อดูรายชื่อพนักงานทั้งหมดในระบบพร้อม Role ปัจจุบัน สามารถเพิ่มบัญชีพนักงานใหม่ แก้ไขข้อมูล/เปลี่ยน Role ของพนักงานที่มีอยู่ และปิดการใช้งานบัญชีพนักงานที่ไม่ต้องการให้เข้าระบบได้อีกต่อไป

**Why this priority**: เป็นความต้องการหลักที่ผู้ใช้ระบุมาโดยตรง ("หน้าจอการจัดการสิทธิ์") ปัจจุบันบัญชีพนักงานถูกสร้างผ่านการ seed ข้อมูลเท่านั้น ไม่มีช่องทางจัดการผ่านหน้าจอ ทำให้ร้านค้าไม่สามารถเพิ่ม/ปลดพนักงานได้เองเมื่อใช้งานจริง ฟีเจอร์นี้ขึ้นกับ User Story 1 เพียงเพราะต้องมีทางเข้าถึงหน้าจอ แต่ตัวฟีเจอร์เองทดสอบแยกได้

**Independent Test**: ล็อกอินด้วยบัญชี Admin เข้าหน้าจอจัดการสิทธิ์โดยตรง (ผ่าน URL หรือเมนู) สร้างบัญชีพนักงานใหม่ กำหนด Role เป็น Cashier ตรวจสอบว่าพนักงานใหม่ล็อกอินได้และเห็นเมนูตาม Role ที่กำหนด จากนั้นปิดใช้งานบัญชีนั้นและตรวจสอบว่าล็อกอินไม่ได้อีก

**Acceptance Scenarios**:

1. **Given** ผู้ดูแลระบบอยู่ในหน้าจอจัดการสิทธิ์, **When** หน้าจอโหลดข้อมูล, **Then** ระบบแสดงรายชื่อพนักงานทั้งหมดพร้อมชื่อผู้ใช้ (username), Role (Cashier/Admin) และสถานะการใช้งาน (เปิด/ปิด)
2. **Given** ผู้ดูแลระบบกรอกฟอร์มเพิ่มพนักงานใหม่ด้วยชื่อผู้ใช้ที่ไม่ซ้ำกับที่มีอยู่, **When** กดบันทึก, **Then** ระบบสร้างบัญชีพนักงานใหม่ พร้อม Role ที่เลือก และบัญชีนั้นสามารถใช้ล็อกอินได้ทันที
3. **Given** ผู้ดูแลระบบกรอกฟอร์มเพิ่มพนักงานใหม่ด้วยชื่อผู้ใช้ที่ซ้ำกับบัญชีที่มีอยู่แล้ว, **When** กดบันทึก, **Then** ระบบแจ้งข้อผิดพลาดว่าชื่อผู้ใช้ซ้ำ และไม่สร้างบัญชีใหม่
4. **Given** มีพนักงานอยู่ในระบบแล้ว, **When** ผู้ดูแลระบบเปลี่ยน Role ของพนักงานคนนั้นจาก Cashier เป็น Admin แล้วบันทึก, **Then** ในการล็อกอินครั้งถัดไปของพนักงานคนนั้น สิทธิ์และเมนูที่เห็นจะเปลี่ยนตาม Role ใหม่
5. **Given** ผู้ดูแลระบบกดปิดใช้งานบัญชีพนักงานคนหนึ่ง, **When** พนักงานคนนั้นพยายามล็อกอินอีกครั้ง, **Then** ระบบปฏิเสธการล็อกอินพร้อมข้อความแจ้งว่าบัญชีถูกปิดใช้งาน
6. **Given** ผู้ดูแลระบบกำลังจะปิดใช้งานบัญชีของตนเอง (บัญชีที่ใช้ล็อกอินอยู่ปัจจุบัน) ซึ่งเป็น Admin คนเดียวที่เหลืออยู่ในระบบ, **When** กดยืนยันปิดใช้งาน, **Then** ระบบปฏิเสธการดำเนินการและแจ้งเตือนว่าต้องมีบัญชี Admin ที่ใช้งานได้อย่างน้อย 1 บัญชีเสมอ
7. **Given** ผู้ใช้ Role "Cashier" พยายามเข้าถึงหน้าจอจัดการสิทธิ์โดยตรงผ่าน URL, **When** ระบบตรวจสอบสิทธิ์, **Then** ระบบปฏิเสธการเข้าถึงและไม่แสดงข้อมูลพนักงานใด ๆ
8. **Given** พนักงานคนหนึ่งลืมรหัสผ่านและแจ้งผู้ดูแลระบบ, **When** ผู้ดูแลระบบเลือกพนักงานคนนั้นในหน้าจอจัดการสิทธิ์ ตั้งรหัสผ่านใหม่ แล้วกดบันทึก, **Then** พนักงานคนนั้นสามารถล็อกอินด้วยรหัสผ่านใหม่ได้ทันที และรหัสผ่านเดิมใช้ล็อกอินไม่ได้อีกต่อไป

---

### Edge Cases

- ผู้ดูแลระบบพยายามลบ/ปิดใช้งานบัญชี Admin คนสุดท้ายในระบบ → ระบบต้องปฏิเสธ (ดู Acceptance Scenario 2.6)
- ผู้ดูแลระบบพยายามเปลี่ยน Role ของตนเองจาก Admin เป็น Cashier ขณะที่เป็น Admin คนเดียวในระบบ → ควรได้รับการปฏิเสธด้วยเหตุผลเดียวกับการปิดใช้งาน (ต้องมี Admin อย่างน้อย 1 คนเสมอ)
- พนักงานที่กำลังล็อกอินอยู่ถูกปิดใช้งานบัญชีหรือเปลี่ยน Role ระหว่างที่ใช้งานระบบอยู่ → ระบบยืนยันตัวตนด้วย JWT แบบ stateless (อายุ token สูงสุด 8 ชั่วโมงตามค่าเดิมของระบบ) จึงไม่มีการเพิกถอน session ที่ login ค้างอยู่ทันที — token เดิมยังใช้งานได้จนกว่าจะหมดอายุตามปกติหรือพนักงานคนนั้น login ใหม่ (ซึ่งตอนนั้นจะได้สิทธิ์ล่าสุด) การปิดใช้งานมีผลแน่นอนกับ "ความพยายาม login ครั้งถัดไป" เสมอ (ตาม FR-011/SC-005) แต่ไม่ได้รับประกันการตัดสิทธิ์ session ที่เปิดค้างอยู่ทันทีในเวอร์ชันนี้ — เป็นข้อจำกัดที่ยอมรับได้ตามสถาปัตยกรรม auth เดิมของระบบ ไม่อยู่ในขอบเขตของฟีเจอร์นี้ที่จะสร้างระบบเพิกถอน token
- ชื่อผู้ใช้ที่กรอกมีช่องว่างหรืออักขระพิเศษที่ไม่รองรับ → ระบบแจ้งข้อผิดพลาดการตรวจสอบความถูกต้องของข้อมูล (validation) ก่อนบันทึก
- จำนวนพนักงานในระบบมีมาก (หลายสิบ-หลายร้อยคน) → หน้าจอจัดการสิทธิ์ต้องรองรับการแบ่งหน้า (pagination) หรือค้นหา/กรองรายชื่อได้
- หน้าจอที่ยังไม่มีในระบบ (เช่น หน้าจัดการสิทธิ์เอง) ต้องถูกเพิ่มเป็นรายการเมนูใหม่และกำหนดสิทธิ์การมองเห็นให้เฉพาะ Admin ตั้งแต่วันแรกที่เปิดใช้งาน

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ระบบต้องแสดงเมนูนำทางกลางที่ปรากฏอยู่บนทุกหน้าจอหลังล็อกอิน โดยไม่แสดงบนหน้าล็อกอิน
- **FR-002**: เมนูนำทางต้องแสดงรายการหน้าจอทั้งหมดที่มีอยู่ในระบบ ได้แก่ ขายสินค้า, สต็อกสินค้า, โปรโมชั่น, ประวัติการขาย, รายงาน และจัดการสิทธิ์ (หน้าใหม่)
- **FR-003**: เมนูนำทางต้องกรองรายการที่แสดงตาม Role ของผู้ใช้ที่ล็อกอินอยู่ โดยแสดงเฉพาะหน้าจอที่ผู้ใช้นั้นมีสิทธิ์เข้าถึงตามกฎสิทธิ์เดิมของระบบ — Cashier เข้าถึงได้เฉพาะ "ขายสินค้า" เท่านั้น (สต็อกสินค้า, โปรโมชั่น, ประวัติการขาย, รายงาน เป็น Admin-only อยู่แล้วตามโค้ดปัจจุบัน) และจัดการสิทธิ์ (หน้าใหม่) เป็น Admin-only เช่นกัน
- **FR-004**: ระบบต้องระบุรายการเมนูของหน้าจอที่ผู้ใช้กำลังเปิดอยู่ในปัจจุบันให้เห็นชัดเจน (active state)
- **FR-005**: การคลิกรายการเมนูต้องพาผู้ใช้ไปยังหน้าจอที่เลือกโดยไม่โหลดหน้าเว็บใหม่ทั้งหมด
- **FR-006**: ระบบต้องมีหน้าจอ "จัดการสิทธิ์" ที่เข้าถึงได้เฉพาะผู้ใช้ Role "Admin" เท่านั้น ทั้งจากเมนูและจากการเรียก URL โดยตรง
- **FR-007**: หน้าจอจัดการสิทธิ์ต้องแสดงรายชื่อพนักงานทั้งหมดในระบบ พร้อมชื่อผู้ใช้, Role และสถานะการใช้งาน (เปิด/ปิด)
- **FR-008**: ผู้ดูแลระบบต้องสามารถเพิ่มบัญชีพนักงานใหม่ผ่านหน้าจอนี้ได้ โดยระบุชื่อผู้ใช้, รหัสผ่านเริ่มต้น, ชื่อที่แสดง และ Role (Cashier หรือ Admin)
- **FR-009**: ระบบต้องปฏิเสธการสร้างบัญชีพนักงานใหม่หากชื่อผู้ใช้ซ้ำกับบัญชีที่มีอยู่แล้ว พร้อมข้อความแจ้งข้อผิดพลาดที่ชัดเจน
- **FR-010**: ผู้ดูแลระบบต้องสามารถแก้ไขข้อมูลพนักงานที่มีอยู่ (ชื่อที่แสดง, Role) ผ่านหน้าจอนี้ได้
- **FR-011**: ผู้ดูแลระบบต้องสามารถเปิด/ปิดการใช้งานบัญชีพนักงานได้ บัญชีที่ถูกปิดใช้งานต้องไม่สามารถล็อกอินเข้าระบบได้อีก
- **FR-012**: ระบบต้องป้องกันไม่ให้ผู้ดูแลระบบปิดใช้งานหรือเปลี่ยน Role ของบัญชี Admin ที่ใช้งานอยู่คนสุดท้ายในระบบ เพื่อไม่ให้ระบบเหลือ Admin ที่ใช้งานได้ 0 คน
- **FR-013**: การเปลี่ยน Role คงเหลือให้ใช้ Role ที่มีอยู่เดิมของระบบ (Cashier, Admin) เท่านั้น เวอร์ชันนี้ยังไม่รองรับการสร้าง Role ใหม่หรือกำหนดสิทธิ์แบบรายฟังก์ชัน/รายหน้าแยกย่อย
- **FR-014**: ระบบต้องบันทึกประวัติว่าใครเป็นผู้สร้าง/แก้ไข/ปิดใช้งาน/รีเซ็ตรหัสผ่านบัญชีพนักงานแต่ละครั้ง เพื่อการตรวจสอบย้อนหลัง การบันทึกนี้เก็บไว้ในระบบเท่านั้น เวอร์ชันนี้ยังไม่ต้องมีหน้าจอแสดงประวัติดังกล่าวให้ผู้ใช้ดู
- **FR-015**: ระบบต้องตรวจสอบความถูกต้องของข้อมูลนำเข้าก่อนบันทึกข้อมูลพนักงาน: ชื่อผู้ใช้ต้องไม่มีช่องว่างและประกอบด้วยตัวอักษร/ตัวเลข/`_`/`.`/`-` เท่านั้น; รหัสผ่านต้องมีความยาวอย่างน้อย 8 ตัวอักษร (ไม่มีข้อกำหนดความซับซ้อนเพิ่มเติมในเวอร์ชันนี้ — ตรวจสอบแล้วว่าโค้ดปัจจุบันไม่มีกฎความยาวรหัสผ่านที่บังคับใช้อยู่ก่อน จึงกำหนดค่าใหม่นี้ขึ้นเป็นครั้งแรก)
- **FR-016**: ผู้ดูแลระบบต้องสามารถตั้งรหัสผ่านใหม่ให้กับบัญชีพนักงานที่มีอยู่แล้วได้โดยตรงผ่านหน้าจอจัดการสิทธิ์ (เพื่อรองรับกรณีพนักงานลืมรหัสผ่าน) โดยรหัสผ่านใหม่มีผลใช้ล็อกอินได้ทันทีและรหัสผ่านเดิมใช้ไม่ได้อีก

### Key Entities *(include if feature involves data)*

- **พนักงาน (Staff)**: บัญชีผู้ใช้งานระบบ มีอยู่แล้วในระบบ ประกอบด้วยชื่อผู้ใช้, รหัสผ่าน (เก็บแบบ hash), ชื่อที่แสดง, Role (Cashier/Admin), สถานะการใช้งาน (เปิด/ปิด) — ฟีเจอร์นี้เพิ่มช่องทางจัดการ (CRUD) ผ่านหน้าจอให้กับเอนทิตีนี้ ไม่ได้สร้างเอนทิตีใหม่
- **รายการเมนู (Menu Item)**: รายการหน้าจอที่แสดงในเมนูนำทาง แต่ละรายการมีชื่อ, เส้นทาง (route) ของหน้าจอ และรายการ Role ที่มีสิทธิ์มองเห็น/เข้าถึงรายการนั้น
- **ประวัติการเปลี่ยนแปลงบัญชีพนักงาน (Staff Audit Log)**: บันทึกว่าใครเป็นผู้กระทำการเปลี่ยนแปลง (สร้าง/แก้ไข/ปิดใช้งาน/รีเซ็ตรหัสผ่าน) กับบัญชีพนักงานคนใด เมื่อใด — เก็บไว้ในระบบเท่านั้น ยังไม่มีหน้าจอแสดงผลในเวอร์ชันนี้

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ผู้ใช้ทุกคนสามารถเข้าถึงทุกหน้าจอที่ตนมีสิทธิ์ใช้งานได้ภายใน 2 คลิกจากเมนูนำทาง โดยไม่ต้องพิมพ์ URL เอง
- **SC-002**: ผู้ดูแลระบบสามารถเพิ่มบัญชีพนักงานใหม่และให้พนักงานคนนั้นล็อกอินใช้งานได้จริงภายในเวลาไม่เกิน 2 นาที โดยไม่ต้องขอความช่วยเหลือจากทีมเทคนิค
- **SC-003**: 100% ของหน้าจอที่สงวนสิทธิ์เฉพาะ Admin (สต็อกสินค้า, โปรโมชั่น, ประวัติการขาย, รายงาน, จัดการสิทธิ์) ปฏิเสธการเข้าถึงจากบัญชี Cashier ทั้งทางเมนูและทางการเรียก URL โดยตรง
- **SC-004**: ระบบไม่ยอมให้เกิดสถานะที่ไม่มีบัญชี Admin ที่ใช้งานได้เหลืออยู่เลยแม้แต่กรณีเดียวในการทดสอบ (0 ครั้งจากการทดสอบ edge case ปิดใช้งาน Admin คนสุดท้าย)
- **SC-005**: ผู้ดูแลระบบสามารถปิดใช้งานบัญชีพนักงานที่ลาออกได้เอง และพนักงานคนนั้นไม่สามารถล็อกอินได้อีกในทันทีที่พยายามครั้งถัดไป

## Assumptions

- เมนูนำทางกลางยังไม่เคยมีอยู่ในระบบมาก่อน ฟีเจอร์นี้จึงรวมการสร้างโครงเมนูนำทาง (navigation shell) ขึ้นใหม่ ไม่ใช่การต่อยอดจากเมนูเดิม
- ระบบสิทธิ์ยังคงใช้ Role คงที่ 2 แบบเดิม (Cashier, Admin) ตามที่มีอยู่แล้วในระบบ การสร้าง Role ใหม่หรือสิทธิ์แบบละเอียดรายฟังก์ชันอยู่นอกขอบเขตของเวอร์ชันนี้
- "จัดการสิทธิ์" ในบริบทนี้หมายถึงการจัดการบัญชีพนักงานและ Role ที่ผูกกับบัญชี ไม่ใช่การจัดการสิทธิ์ของลูกค้า/สมาชิก
- รหัสผ่านเริ่มต้นที่ผู้ดูแลระบบตั้งให้พนักงานใหม่ และรหัสผ่านที่ผู้ดูแลระบบตั้งใหม่ให้เมื่อรีเซ็ต (FR-016) ต้องมีความยาวอย่างน้อย 8 ตัวอักษรตาม FR-015 (ก่อนหน้านี้ระบบไม่มีกฎความยาวรหัสผ่านบังคับใช้เลย — นี่คือกฎใหม่ที่กำหนดขึ้นในฟีเจอร์นี้) ยังไม่รวมฟีเจอร์บังคับเปลี่ยนรหัสผ่านครั้งแรกหรือระบบ "ลืมรหัสผ่าน" แบบ self-service (เช่น ลิงก์รีเซ็ตทางอีเมล) ในเวอร์ชันนี้ — การรีเซ็ตรหัสผ่านทำผ่าน Admin เท่านั้น
- ผู้ดูแลระบบเป็นผู้รับผิดชอบแจ้งชื่อผู้ใช้/รหัสผ่านเริ่มต้นให้พนักงานใหม่ทราบเอง (นอกระบบ เช่น ปากเปล่าหรือกระดาษ) ระบบไม่ต้องส่งอีเมล/SMS แจ้งเตือนอัตโนมัติ
- การลบบัญชีพนักงานแบบถาวร (hard delete) ไม่อยู่ในขอบเขต ใช้การ "ปิดใช้งาน" (soft disable) แทนเพื่อรักษาความสัมพันธ์กับประวัติการขายเดิมของพนักงานคนนั้น
