# Feature Specification: ระบบ POS สำหรับร้านขายผลไม้และสินค้าทั่วไป (Single Store)

**Feature Branch**: `001-pos-system`

**Created**: 2026-09-10

**Status**: Draft

**Input**: User description: "สร้างระบบ POS (Point of Sale) สำหรับร้านขายผลไม้และสินค้าทั่วไป มี requirement: หน้าขายสินค้า, ระบบสมาชิก, ระบบพนักงานขาย, ระบบสต็อกสินค้า, ระบบโปรโมชั่น, การบันทึกยอดขาย, รายงาน. ขอบเขต: ร้านค้าเดี่ยว (single store) ไม่รองรับหลายสาขาในเวอร์ชันนี้"

## Clarifications

### Session 2026-09-10

- Q: เมื่อพนักงานขายผิดพลาดหรือลูกค้าขอคืนสินค้าหลังชำระเงินแล้ว ระบบควรรองรับการยกเลิก/คืนบิลในเวอร์ชันนี้หรือไม่ และในรูปแบบใด? → A: รองรับการยกเลิกบิลแบบเต็มจำนวนเท่านั้น (void ทั้งบิล คืนสต็อกกลับ) ภายในวันเดียวกับที่ขาย ไม่รองรับการคืนสินค้าบางส่วน
- Q: หากอินเทอร์เน็ตหรือเครือข่ายภายในร้านขัดข้องระหว่างเวลาทำการ หน้าขายสินค้าควรทำงานอย่างไร? → A: หน้าขายต้องเชื่อมต่อเซิร์ฟเวอร์ตลอดเวลา หากขาดการเชื่อมต่อจะไม่สามารถทำรายการขายได้จนกว่าจะเชื่อมต่อกลับมา (ไม่รองรับโหมดออฟไลน์ในเวอร์ชันนี้)
- Q: พนักงานควรล็อกอินเข้าหน้าขายด้วยวิธีใด? → A: ชื่อผู้ใช้และรหัสผ่านแบบมาตรฐาน
- Q: บาร์โค้ดของสินค้าจำเป็นต้องมีครบทุกชิ้นและห้ามซ้ำกันหรือไม่? → A: บาร์โค้ดเป็นทางเลือก (ไม่บังคับ) แต่ถ้ามีต้องไม่ซ้ำกันระหว่างสินค้า

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ขายสินค้าหน้าร้าน (Priority: P1)

พนักงานล็อกอินเข้าหน้าขาย ค้นหา/เลือกสินค้าจากการ์ดสินค้าที่มีรูปภาพ เพิ่มลงตะกร้า ปรับจำนวนหรือเอาออกได้ก่อนกดชำระเงิน เมื่อชำระเงินสำเร็จระบบตัดสต็อกอัตโนมัติและบันทึกบิลพร้อมชื่อพนักงานที่ขาย

**Why this priority**: เป็นแกนหลักของระบบ POS — หากทำไม่ได้ ร้านค้าไม่สามารถใช้ระบบขายสินค้าได้เลย ฟีเจอร์อื่นทั้งหมด (สมาชิก โปรโมชั่น รายงาน) เป็นส่วนต่อยอดจากธุรกรรมการขายนี้

**Independent Test**: สามารถทดสอบได้ครบวงจรโดยเพิ่มสินค้าตัวอย่างในระบบ (ผ่าน User Story 2), ให้พนักงานล็อกอิน, ค้นหาสินค้าด้วยชื่อและบาร์โค้ด, เพิ่ม/ลด/ลบสินค้าในตะกร้า, กดชำระเงิน แล้วตรวจสอบว่าสต็อกลดลงตามจำนวนที่ขายและมีบันทึกบิลใหม่เกิดขึ้นพร้อมชื่อพนักงาน

**Acceptance Scenarios**:

1. **Given** พนักงานล็อกอินเข้าหน้าขายแล้ว และมีสินค้า "มะม่วง" อยู่ในสต็อก 20 ชิ้น, **When** พนักงานค้นหาคำว่า "มะม่วง" กดเพิ่มลงตะกร้า 3 ชิ้น แล้วกดชำระเงิน, **Then** ระบบสร้างบิลขายใหม่ที่มีรายการมะม่วง 3 ชิ้น ผูกกับพนักงานคนที่ขาย และสต็อกมะม่วงลดลงเหลือ 17 ชิ้น
2. **Given** พนักงานสแกน/พิมพ์บาร์โค้ดของสินค้าชิ้นหนึ่ง, **When** บาร์โค้ดตรงกับสินค้าในระบบ, **Then** สินค้านั้นถูกเพิ่มลงตะกร้าโดยอัตโนมัติ
3. **Given** ตะกร้ามีสินค้าอยู่แล้ว, **When** พนักงานลดจำนวนสินค้าชิ้นหนึ่งลงเหลือ 0 หรือกดลบสินค้านั้นออก, **Then** สินค้านั้นหายไปจากตะกร้าและยอดรวมบิลอัปเดตทันที
4. **Given** พนักงานยังไม่ได้ล็อกอิน, **When** พยายามเข้าหน้าขายสินค้า, **Then** ระบบปฏิเสธการเข้าถึงและนำไปหน้าล็อกอิน
5. **Given** บิลขายถูกสร้างและชำระเงินสำเร็จในวันนี้, **When** ผู้ดูแลร้านกดยกเลิก (void) บิลนั้นทั้งใบภายในวันเดียวกัน, **Then** ระบบคืนจำนวนสินค้าทุกรายการในบิลนั้นกลับเข้าสต็อก และบันทึกสถานะบิลเป็น "ยกเลิกแล้ว" โดยไม่นับรวมในรายงานยอดขาย

### User Story 2 - จัดการสต็อกสินค้า (Priority: P2)

ผู้ดูแลร้านเพิ่ม/แก้ไข/ลบข้อมูลสินค้า พร้อมรูปภาพ ราคา และจำนวนคงเหลือ เพื่อให้มีสินค้าให้ขายในหน้าขาย และได้รับการแจ้งเตือนเมื่อสินค้าใกล้หมด

**Why this priority**: หน้าขาย (P1) ต้องพึ่งพาข้อมูลสินค้าที่มีอยู่ในระบบ แต่การจัดการสต็อกเป็นงานที่ทำแยกต่างหากจากธุรกรรมขาย (มักทำโดยผู้ดูแลร้าน ไม่ใช่แคชเชียร์) จึงทดสอบและส่งมอบแยกจาก P1 ได้ แม้ P1 จะต้องมีสินค้าตัวอย่างอย่างน้อยจึงจะสาธิตได้ครบ

**Independent Test**: สามารถทดสอบได้อิสระโดยเพิ่มสินค้าใหม่พร้อมรูปภาพ ราคา และจำนวนคงเหลือ, แก้ไขราคา/จำนวน, ลบสินค้า, และตั้งจำนวนคงเหลือให้ต่ำกว่าจุดแจ้งเตือนเพื่อตรวจสอบว่าระบบแจ้งเตือนสินค้าใกล้หมด — ทั้งหมดนี้ทำได้โดยไม่ต้องมีธุรกรรมขายเกิดขึ้นเลย

**Acceptance Scenarios**:

1. **Given** ผู้ดูแลร้านอยู่หน้าจัดการสต็อก, **When** เพิ่มสินค้าใหม่พร้อมชื่อ รูปภาพ ราคา และจำนวนคงเหลือ, **Then** สินค้านั้นปรากฏในหน้าขายและพร้อมให้ค้นหา/เลือกขายได้ทันที
2. **Given** สินค้าชิ้นหนึ่งมีจำนวนคงเหลือลดลงจนถึงเกณฑ์ใกล้หมดที่กำหนดไว้, **When** ระบบตรวจพบ, **Then** ระบบแสดงการแจ้งเตือนสินค้าใกล้หมดให้ผู้ดูแลร้านเห็น
3. **Given** ผู้ดูแลร้านแก้ไขราคาหรือรูปภาพของสินค้า, **When** บันทึกการแก้ไข, **Then** หน้าขายแสดงข้อมูลสินค้าใหม่ทันทีโดยไม่กระทบบิลที่ขายไปแล้วก่อนหน้า
4. **Given** สินค้าชิ้นหนึ่งถูกลบออกจากระบบ, **When** พนักงานค้นหาสินค้านั้นในหน้าขาย, **Then** ไม่พบสินค้านั้นให้เลือกขายอีกต่อไป แต่ประวัติบิลเก่าที่เคยขายสินค้านั้นยังแสดงข้อมูลเดิมได้ครบถ้วน

### User Story 3 - ระบบสมาชิกและส่วนลดสมาชิก (Priority: P3)

พนักงานสมัครสมาชิกใหม่ด้วยเบอร์โทรและชื่อ ค้นหาสมาชิกที่มีอยู่ตอนขายเพื่อผูกยอดซื้อสะสมและให้สิทธิ์ส่วนลดพิเศษสำหรับสมาชิก

**Why this priority**: เพิ่มมูลค่าทางธุรกิจ (ลูกค้าประจำ ยอดซื้อสะสม) แต่ไม่ใช่เงื่อนไขจำเป็นสำหรับการขายพื้นฐาน ระบบขาย (P1) ต้องทำงานได้แม้ไม่มีสมาชิกเข้าร่วมในบิล

**Independent Test**: สามารถทดสอบได้อิสระโดยสมัครสมาชิกใหม่ด้วยเบอร์โทรและชื่อ, ค้นหาสมาชิกด้วยเบอร์โทรตอนขาย, ผูกบิลกับสมาชิกนั้น แล้วตรวจสอบว่ายอดซื้อสะสมของสมาชิกเพิ่มขึ้นตามยอดบิล และส่วนลดสมาชิกถูกคำนวณเข้าไปในยอดชำระ

**Acceptance Scenarios**:

1. **Given** พนักงานอยู่หน้าสมัครสมาชิก, **When** กรอกเบอร์โทรและชื่อที่ยังไม่เคยสมัคร แล้วบันทึก, **Then** ระบบสร้างสมาชิกใหม่ที่มียอดซื้อสะสมเริ่มต้นเป็น 0
2. **Given** มีสมาชิกอยู่ในระบบแล้ว, **When** พนักงานค้นหาด้วยเบอร์โทรระหว่างทำรายการขาย, **Then** ระบบผูกบิลนั้นกับสมาชิกที่พบ และแสดงสิทธิ์ส่วนลดสมาชิกให้เลือกใช้
3. **Given** บิลถูกผูกกับสมาชิกและชำระเงินสำเร็จ, **When** ระบบบันทึกบิล, **Then** ยอดซื้อสะสมของสมาชิกคนนั้นเพิ่มขึ้นตามยอดสุทธิของบิล
4. **Given** พนักงานค้นหาเบอร์โทรที่ไม่มีในระบบ, **When** ไม่พบสมาชิก, **Then** ระบบแจ้งว่าไม่พบสมาชิกและเสนอทางเลือกให้สมัครสมาชิกใหม่หรือขายแบบไม่ระบุสมาชิกต่อไป

### User Story 4 - ระบบโปรโมชั่น (Priority: P4)

ผู้ดูแลร้านตั้งส่วนลดเป็น % ต่อสินค้าหรือทั้งบิล กำหนดช่วงวันที่เริ่ม-สิ้นสุด และระบบนำโปรโมชั่นที่ยังมีผลไปคำนวณส่วนลดให้อัตโนมัติตอนขาย

**Why this priority**: เป็นเครื่องมือกระตุ้นยอดขายที่ต่อยอดจากการขายพื้นฐาน (P1) และทำงานร่วมกับส่วนลดสมาชิก (P3) แต่ระบบขายต้องทำงานได้สมบูรณ์อยู่แล้วแม้ไม่มีโปรโมชั่นใดๆ ที่มีผลในขณะนั้น

**Independent Test**: สามารถทดสอบได้อิสระโดยตั้งโปรโมชั่นส่วนลด % ให้สินค้าหนึ่งรายการหรือทั้งบิล พร้อมกำหนดวันเริ่ม-สิ้นสุด แล้วตรวจสอบว่าระบบใช้ส่วนลดนั้นถูกต้องเฉพาะช่วงวันที่ที่กำหนดเมื่อขายสินค้าที่เข้าเงื่อนไข และไม่ใช้ส่วนลดนอกช่วงวันที่หรือกับสินค้าที่ไม่เข้าเงื่อนไข

**Acceptance Scenarios**:

1. **Given** ผู้ดูแลร้านตั้งโปรโมชั่นลด 10% ให้สินค้า "แอปเปิ้ล" ตั้งแต่วันนี้ถึงสิ้นเดือน, **When** พนักงานขายแอปเปิ้ลในช่วงวันที่ดังกล่าว, **Then** ระบบลดราคาแอปเปิ้ลลง 10% ในบิลโดยอัตโนมัติ
2. **Given** โปรโมชั่นลด 5% ทั้งบิลถูกตั้งไว้และยังไม่ถึงวันเริ่ม, **When** พนักงานขายสินค้าที่เข้าเงื่อนไขในวันนี้, **Then** ระบบยังไม่ใช้ส่วนลดนั้นเพราะยังไม่ถึงวันเริ่มโปรโมชั่น
3. **Given** โปรโมชั่นสิ้นสุดไปแล้วเมื่อวานนี้, **When** พนักงานขายสินค้าที่เคยเข้าเงื่อนไขในวันนี้, **Then** ระบบไม่ใช้ส่วนลดของโปรโมชั่นที่หมดอายุแล้ว
4. **Given** บิลมีทั้งส่วนลดโปรโมชั่นทั่วไปและส่วนลดสมาชิก, **When** ระบบคำนวณยอดสุทธิ, **Then** ระบบแสดงรายละเอียดส่วนลดแต่ละประเภทแยกจากกันอย่างชัดเจนในบิล

### User Story 5 - ประวัติการขายและรายงาน (Priority: P5)

เจ้าของร้านหรือผู้ดูแลดูประวัติบิลขายย้อนหลัง และเรียกดูรายงานยอดขายรายวัน/รายเดือน สินค้าขายดี ยอดขายแยกตามพนักงาน และสต็อกคงเหลือ เพื่อใช้ตัดสินใจบริหารร้าน

**Why this priority**: เป็นการวิเคราะห์ข้อมูลที่เกิดจากการขาย (P1) และสต็อก (P2) ที่สะสมไว้แล้ว มีคุณค่าสูงต่อการบริหารร้านแต่ไม่กระทบการทำงานประจำวันของหน้าขาย จึงพัฒนาและส่งมอบเป็นลำดับสุดท้ายได้

**Independent Test**: สามารถทดสอบได้อิสระโดยใช้ข้อมูลบิลขายและสต็อกที่มีอยู่แล้วในระบบ (จากการทดสอบ P1/P2) แล้วเรียกดูรายงานแต่ละประเภท ตรวจสอบว่าตัวเลขในรายงานตรงกับผลรวมของข้อมูลบิล/สต็อกที่มีอยู่จริง

**Acceptance Scenarios**:

1. **Given** มีบิลขายเกิดขึ้นหลายรายการในเดือนนี้, **When** ผู้ดูแลเปิดรายงานยอดขายรายเดือน, **Then** ระบบแสดงยอดขายรวมของเดือนนั้นตรงกับผลรวมของทุกบิลในเดือนนั้น
2. **Given** มีการขายสินค้าหลายรายการในช่วงเวลาหนึ่ง, **When** ผู้ดูแลเปิดรายงานสินค้าขายดี, **Then** ระบบจัดอันดับสินค้าตามจำนวน/ยอดขายจากมากไปน้อยได้ถูกต้อง
3. **Given** พนักงานหลายคนขายสินค้าในช่วงเวลาเดียวกัน, **When** ผู้ดูแลเปิดรายงานยอดขายแยกตามพนักงาน, **Then** ยอดขายของแต่ละคนตรงกับผลรวมบิลที่ผูกกับพนักงานคนนั้น
4. **Given** ผู้ดูแลต้องการตรวจสอบบิลเก่า, **When** ค้นหาประวัติการขายย้อนหลังตามช่วงวันที่, **Then** ระบบแสดงรายการบิลที่ตรงเงื่อนไขพร้อมรายละเอียดสินค้า ราคา ส่วนลด พนักงาน และสมาชิก (ถ้ามี) ของแต่ละบิล

### Edge Cases

- ตะกร้ามีสินค้าค้างอยู่ แต่ระหว่างนั้นสต็อกสินค้าถูกปรับลดจนไม่พอขาย (เช่น พนักงานอีกคนขายไปพร้อมกัน) — ระบบต้องแจ้งเตือนและปฏิเสธการชำระเงินสำหรับจำนวนที่เกินสต็อกคงเหลือ
- บาร์โค้ดที่สแกน/พิมพ์ไม่ตรงกับสินค้าใดในระบบ — ระบบต้องแจ้งว่าไม่พบสินค้าและไม่เพิ่มรายการใดลงตะกร้า
- สมัครสมาชิกด้วยเบอร์โทรที่มีอยู่แล้วในระบบ — ระบบต้องแจ้งว่าเบอร์นี้เป็นสมาชิกอยู่แล้วแทนที่จะสร้างสมาชิกซ้ำ
- โปรโมชั่นสองรายการเข้าเงื่อนไขกับสินค้าชิ้นเดียวกันพร้อมกัน (เช่น ส่วนลดต่อสินค้า และส่วนลดทั้งบิล) — ระบบต้องมีกติกาการรวม/เลือกใช้ส่วนลดที่ชัดเจนและสม่ำเสมอ ไม่ปล่อยให้ราคาติดลบ
- สินค้าที่เคยขายไปแล้วถูกลบออกจากสต็อกภายหลัง — ประวัติบิลเก่าต้องยังคงแสดงชื่อ/ราคาสินค้า ณ เวลาที่ขายได้ครบถ้วน แม้สินค้าจะไม่มีอยู่ในสต็อกปัจจุบันแล้ว
- พนักงานถูกล็อกเอาต์ (หมดเซสชัน) ขณะมีสินค้าค้างอยู่ในตะกร้าที่ยังไม่ชำระเงิน — ต้องกำหนดว่าตะกร้านั้นจะถูกเก็บไว้รอหรือถูกล้างทิ้ง
- จำนวนสินค้าที่ใส่ในตะกร้าเป็น 0 หรือค่าติดลบ — ระบบต้องป้องกันไม่ให้เกิดรายการที่มีจำนวนไม่ถูกต้องในบิล
- ระบบขาดการเชื่อมต่อเครือข่าย/เซิร์ฟเวอร์ขณะพนักงานกำลังกดชำระเงิน — ระบบต้องปฏิเสธการทำรายการทั้งหมด ไม่บันทึกบิลบางส่วน และแจ้งพนักงานให้ลองใหม่หลังเชื่อมต่อกลับมาได้
- พนักงานพยายามยกเลิก (void) บิลที่ขายข้ามวันไปแล้ว — ระบบต้องปฏิเสธการยกเลิกเพราะเกินระยะเวลาที่อนุญาต (ยกเลิกได้เฉพาะบิลที่ขายในวันเดียวกันเท่านั้น)
- บิลถูกยกเลิก (void) แล้ว — ระบบต้องคืนจำนวนสินค้าทุกรายการในบิลนั้นกลับเข้าสต็อกโดยอัตโนมัติ และห้ามยกเลิกบิลเดียวกันซ้ำอีกครั้ง

## Requirements *(mandatory)*

### Functional Requirements

**หน้าขายสินค้า**

- **FR-001**: ระบบต้องแสดงรายการสินค้าเป็นการ์ด/ไอคอนพร้อมรูปภาพ ให้พนักงานเลือกกดเพิ่มลงตะกร้าได้โดยตรง
- **FR-002**: ระบบต้องรองรับการค้นหาสินค้าด้วยชื่อสินค้าหรือบาร์โค้ด และแสดงผลลัพธ์ที่ตรงกับคำค้นหาแบบทันที
- **FR-003**: ระบบต้องอนุญาตให้พนักงานเพิ่ม ลดจำนวน หรือลบสินค้าออกจากตะกร้าได้ก่อนยืนยันชำระเงิน
- **FR-004**: ระบบต้องคำนวณยอดรวมของตะกร้าใหม่ทันทีทุกครั้งที่มีการเปลี่ยนแปลงรายการในตะกร้า
- **FR-005**: ระบบต้องปฏิเสธการชำระเงินหากจำนวนสินค้าที่ขอซื้อในตะกร้ามากกว่าจำนวนคงเหลือในสต็อก ณ เวลาชำระเงิน
- **FR-006**: หน้าขายสินค้าต้องเชื่อมต่อกับเซิร์ฟเวอร์ตลอดเวลาที่ใช้งาน หากขาดการเชื่อมต่อ ระบบต้องปฏิเสธการทำรายการขายทั้งหมด (ไม่บันทึกบิลบางส่วน) จนกว่าจะเชื่อมต่อได้อีกครั้ง

**ระบบพนักงานขาย**

- **FR-007**: ระบบต้องกำหนดให้พนักงานล็อกอินด้วยชื่อผู้ใช้และรหัสผ่านก่อนจึงจะเข้าใช้งานหน้าขายสินค้าได้
- **FR-008**: ระบบต้องบันทึกพนักงานผู้ทำรายการไว้กับทุกบิลขายที่เกิดขึ้น

**ระบบสต็อกสินค้า**

- **FR-009**: ระบบต้องอนุญาตให้ผู้ดูแลร้านเพิ่มสินค้าใหม่พร้อมชื่อ รูปภาพ ราคา และจำนวนคงเหลือ
- **FR-010**: ระบบต้องอนุญาตให้ผู้ดูแลร้านแก้ไขข้อมูลสินค้า (ชื่อ รูปภาพ ราคา จำนวนคงเหลือ) ที่มีอยู่
- **FR-011**: ระบบต้องอนุญาตให้ผู้ดูแลร้านลบสินค้าออกจากรายการที่ขายได้ โดยไม่ลบข้อมูลสินค้านั้นออกจากบิลขายที่เกิดขึ้นแล้วในอดีต
- **FR-012**: ระบบต้องตัดจำนวนคงเหลือในสต็อกโดยอัตโนมัติตามจำนวนที่ขายได้ทันทีที่การชำระเงินสำเร็จ
- **FR-013**: ระบบต้องแจ้งเตือนผู้ดูแลร้านเมื่อจำนวนคงเหลือของสินค้าลดลงถึงหรือต่ำกว่าเกณฑ์ใกล้หมดที่กำหนดไว้ต่อสินค้าแต่ละชิ้น
- **FR-014**: บาร์โค้ดของสินค้าเป็นข้อมูลทางเลือก (ไม่บังคับต้องมี) แต่หากสินค้าใดถูกระบุบาร์โค้ด ระบบต้องป้องกันไม่ให้บาร์โค้ดนั้นซ้ำกับสินค้าอื่นในระบบ

**ระบบสมาชิก**

- **FR-015**: ระบบต้องอนุญาตให้สมัครสมาชิกใหม่ด้วยเบอร์โทรศัพท์และชื่อ
- **FR-016**: ระบบต้องป้องกันการสมัครสมาชิกซ้ำด้วยเบอร์โทรศัพท์ที่มีอยู่แล้วในระบบ
- **FR-017**: ระบบต้องอนุญาตให้พนักงานค้นหาสมาชิกด้วยเบอร์โทรศัพท์ระหว่างทำรายการขาย
- **FR-018**: ระบบต้องผูกยอดซื้อสะสมของสมาชิกเข้ากับทุกบิลที่ระบุสมาชิกนั้น และปรับยอดสะสมเพิ่มขึ้นเมื่อบิลชำระเงินสำเร็จ
- **FR-019**: ระบบต้องอนุญาตให้ใช้สิทธิ์ส่วนลดสมาชิกกับบิลที่ผูกกับสมาชิกคนนั้น

**ระบบโปรโมชั่น**

- **FR-020**: ระบบต้องอนุญาตให้ผู้ดูแลร้านตั้งส่วนลดเป็นเปอร์เซ็นต์สำหรับสินค้ารายชิ้นหรือสำหรับทั้งบิล
- **FR-021**: ระบบต้องอนุญาตให้ผู้ดูแลร้านตั้งส่วนลดพิเศษสำหรับสมาชิกเป็นเปอร์เซ็นต์ แยกต่างหากจากโปรโมชั่นทั่วไป
- **FR-022**: ระบบต้องอนุญาตให้ผู้ดูแลร้านกำหนดวันที่เริ่มต้นและสิ้นสุดของแต่ละโปรโมชั่น
- **FR-023**: ระบบต้องใช้โปรโมชั่นกับบิลขายเฉพาะเมื่อวันที่ทำรายการขายอยู่ในช่วงวันที่เริ่ม-สิ้นสุดของโปรโมชั่นนั้นเท่านั้น
- **FR-024**: ระบบต้องแสดงรายละเอียดส่วนลดแต่ละประเภท (โปรโมชั่นทั่วไปและส่วนลดสมาชิก) แยกจากกันในบิล

**การบันทึกยอดขาย**

- **FR-025**: ระบบต้องบันทึกทุกบิลขายพร้อมรายการสินค้า ราคาต่อหน่วย จำนวน ส่วนลดที่ใช้ พนักงานผู้ขาย และสมาชิก (ถ้ามี)
- **FR-026**: ระบบต้องอนุญาตให้ผู้ดูแลค้นหาและดูรายละเอียดประวัติบิลขายย้อนหลังตามช่วงวันที่
- **FR-027**: ระบบต้องอนุญาตให้ผู้มีสิทธิ์ยกเลิก (void) บิลขายที่ชำระเงินแล้วได้แบบเต็มจำนวนเท่านั้น (ไม่รองรับการคืนสินค้าบางส่วน) และทำได้เฉพาะภายในวันเดียวกับที่ขายเท่านั้น
- **FR-028**: เมื่อบิลถูกยกเลิก (void) ระบบต้องคืนจำนวนสินค้าทุกรายการในบิลนั้นกลับเข้าสต็อกโดยอัตโนมัติ บันทึกสถานะบิลเป็น "ยกเลิกแล้ว" และห้ามยกเลิกบิลเดียวกันซ้ำอีก

**รายงาน**

- **FR-029**: ระบบต้องแสดงรายงานยอดขายรวมแบบรายวันและรายเดือน
- **FR-030**: ระบบต้องแสดงรายงานจัดอันดับสินค้าขายดีตามช่วงเวลาที่เลือก
- **FR-031**: ระบบต้องแสดงรายงานยอดขายแยกตามพนักงานแต่ละคน
- **FR-032**: ระบบต้องแสดงรายงานจำนวนสินค้าคงเหลือในสต็อก ณ ปัจจุบัน
- **FR-033**: รายงานยอดขายและสินค้าขายดีต้องไม่นับรวมบิลที่ถูกยกเลิก (void) แล้ว

**การยืนยันตัวตนและสิทธิ์การใช้งาน**

- **FR-034**: ระบบต้องรองรับบัญชีผู้ใช้งานอย่างน้อยสองระดับสิทธิ์: พนักงานขาย (เข้าหน้าขายและสมัครสมาชิกได้) และผู้ดูแลร้าน (เข้าถึงการจัดการสต็อก โปรโมชั่น รายงาน และยกเลิกบิลได้เพิ่มเติมจากสิทธิ์พนักงานขาย)
- **FR-035**: ระบบต้องรองรับการชำระเงินด้วยเงินสดเป็นวิธีการชำระเงินหลักสำหรับเวอร์ชันนี้
- **FR-036**: เมื่อบิลมีทั้งส่วนลดโปรโมชั่นทั่วไปและส่วนลดสมาชิกที่เข้าเงื่อนไขพร้อมกัน ระบบต้องรวมส่วนลดทั้งสองประเภทเข้าด้วยกันในบิลเดียว โดยคำนวณแบบลดต่อเนื่อง (ลดโปรโมชั่นทั่วไปก่อน แล้วจึงลดส่วนลดสมาชิกจากยอดที่เหลือ) และยอดสุทธิต้องไม่ต่ำกว่าศูนย์

### Key Entities *(include if feature involves data)*

- **สินค้า (Product)**: ชื่อ รูปภาพ บาร์โค้ด (ไม่บังคับ แต่ถ้ามีต้องไม่ซ้ำกัน) ราคาขาย จำนวนคงเหลือในสต็อก เกณฑ์แจ้งเตือนสินค้าใกล้หมด สถานะเปิด/ปิดการขาย
- **พนักงาน (Staff)**: ชื่อ ชื่อผู้ใช้และรหัสผ่านสำหรับล็อกอิน ระดับสิทธิ์ (พนักงานขาย/ผู้ดูแลร้าน)
- **สมาชิก (Member)**: ชื่อ เบอร์โทรศัพท์ (ห้ามซ้ำกัน) ยอดซื้อสะสม วันที่สมัคร
- **โปรโมชั่น (Promotion)**: ประเภทส่วนลด (ต่อสินค้า/ทั้งบิล/สมาชิก) เปอร์เซ็นต์ส่วนลด วันที่เริ่มต้น วันที่สิ้นสุด สินค้าที่เกี่ยวข้อง (ถ้าเป็นส่วนลดต่อสินค้า)
- **บิลขาย (Sales Order)**: วันที่และเวลาทำรายการ พนักงานผู้ขาย สมาชิกที่ผูกด้วย (ถ้ามี) รายการสินค้าที่ขายพร้อมราคาและจำนวน ส่วนลดที่ใช้แต่ละประเภท ยอดรวมก่อนและหลังส่วนลด สถานะบิล (ปกติ/ยกเลิกแล้ว)
- **รายการสินค้าในบิล (Sales Order Line)**: สินค้าที่ขาย ราคาต่อหน่วย ณ เวลาที่ขาย จำนวนที่ขาย ส่วนลดที่ใช้กับรายการนั้น

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: พนักงานสามารถทำรายการขายสินค้า 5 ชิ้นตั้งแต่ค้นหาสินค้าจนถึงชำระเงินเสร็จสิ้นได้ภายใน 1 นาที
- **SC-002**: หลังชำระเงินสำเร็จ จำนวนคงเหลือในสต็อกของสินค้าที่ขายอัปเดตถูกต้อง 100% ของกรณีทดสอบ
- **SC-003**: 95% ของการค้นหาสินค้าด้วยชื่อหรือบาร์โค้ดแสดงผลลัพธ์ที่ถูกต้องภายใน 1 วินาที
- **SC-004**: ผู้ดูแลร้านสามารถเรียกดูรายงานยอดขายรายวันหรือรายเดือนที่มีตัวเลขตรงกับผลรวมของบิลขายจริง 100% ของกรณีทดสอบ
- **SC-005**: บิลที่มีส่วนลดโปรโมชั่นและ/หรือส่วนลดสมาชิกคำนวณยอดสุทธิถูกต้อง 100% ของกรณีทดสอบ เทียบกับการคำนวณด้วยมือ
- **SC-006**: ผู้ดูแลร้านได้รับการแจ้งเตือนสินค้าใกล้หมดภายในเวลาที่สินค้านั้นลดลงถึงเกณฑ์ที่ตั้งไว้ ไม่มีกรณีสินค้าหมดสต็อกโดยไม่มีการแจ้งเตือนล่วงหน้า
- **SC-007**: เมื่อเครือข่ายขัดข้องระหว่างทำรายการขาย ระบบไม่สร้างบิลที่มีข้อมูลไม่สมบูรณ์ 100% ของกรณีทดสอบ (ทำรายการสำเร็จทั้งหมดหรือไม่สำเร็จเลย)

## Assumptions

- ร้านค้ามีสาขาเดียว (single store) ไม่ต้องรองรับการจัดการหลายสาขาหรือโอนสต็อกระหว่างสาขาในเวอร์ชันนี้
- อุปกรณ์ที่ใช้งานหน้าขายเชื่อมต่ออินเทอร์เน็ต/เครือข่ายภายในร้านได้อย่างเสถียรระหว่างเวลาทำการ ระบบไม่ต้องรองรับโหมดออฟไลน์ในเวอร์ชันนี้ (ยืนยันแล้วใน Clarifications)
- การชำระเงินในเวอร์ชันนี้พิจารณาเป็นเงินสดเป็นหลัก ส่วนช่องทางชำระเงินอื่น (โอน/QR/บัตร) อยู่นอกขอบเขตของเวอร์ชันนี้ และสามารถเพิ่มเป็นฟีเจอร์ในอนาคตได้
- พนักงานขายและผู้ดูแลร้านเป็นสองระดับสิทธิ์เดียวที่จำเป็นสำหรับเวอร์ชันนี้ ยังไม่ต้องรองรับสิทธิ์ย่อยเพิ่มเติม (เช่น ผู้จัดการกะ)
- เกณฑ์ "สินค้าใกล้หมด" ตั้งค่าได้ต่อสินค้าแต่ละชิ้นโดยผู้ดูแลร้าน หากไม่ได้ตั้งค่าจะใช้ค่าเริ่มต้นที่กำหนดไว้ในระบบ
- ประวัติบิลขายเก็บไว้ไม่มีกำหนดวันหมดอายุในเวอร์ชันนี้ (ไม่ลบทิ้งอัตโนมัติ) รวมถึงบิลที่ถูกยกเลิก (void) แล้วก็ยังเก็บประวัติไว้เพื่อการตรวจสอบ
- การยกเลิกบิล (void) รองรับเฉพาะแบบเต็มจำนวนและเฉพาะภายในวันเดียวกับที่ขายเท่านั้น การคืนสินค้าบางส่วนหรือการยกเลิกบิลข้ามวันอยู่นอกขอบเขตของเวอร์ชันนี้
